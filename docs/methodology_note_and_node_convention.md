# Methodology Note: NVD's AND-Node CPE Convention for Embedded/IoT Devices

## Citable result

Across the v2 window-distributed stratified pilot sample (200 records spanning
1999-2026, retrieved 2026-09-05 -- see [`docs/pilot_report_v2.md`](pilot_report_v2.md)),
the legacy convention of marking a `part:h` (hardware) CPE `vulnerable: true`
is measurable as a convention that was near-universal through the early
2010s and is now extinct:

- **1999-2011:** `h_vulnerable_true` fires on all or nearly all matched
  records in the pre-2024 stratum's sampled year-windows (see per-year table
  below).
- **2012-2016:** transitional decline.
- **2017 onward, across the entire 133-record backlog + triage stratum
  (2024-2026):** `h_vulnerable_true` = **0 of 133**.
- **Overall:** `h_vulnerable_true` = **43 of 200** (all 43 in the pre-2024
  stratum).

## What is the AND-node convention?

Modern NVD tags an embedded/IoT vulnerability using two ANDed CPE match
criteria inside a single configuration node:

- a `part:o` (operating system/firmware) CPE identifying the actual
  vulnerable firmware (e.g. `cpe:2.3:o:dlink:dir-822_firmware:*`), marked
  `vulnerable: true`; and
- a `part:h` (hardware) CPE identifying the physical device the firmware
  runs on (e.g. `cpe:2.3:h:dlink:dir-822:-`), marked `vulnerable: false` --
  it is the "runs on" target, not itself the vulnerable component.

A filter that requires `part:h AND vulnerable:true` therefore excludes
essentially every CVE tagged this way. Per the measured data above, that is
effectively **all** embedded/IoT CVEs published since ~2017, and a rapidly
increasing share from 2012 onward. See [`src/corpus_filter.py`](../src/corpus_filter.py)
for the corrected rule (`h_any` / Include A: match `part:h` regardless of
the `vulnerable` flag; `o_firmware` / Include C: match `part:o` products
ending in `_firmware`).

## Correction note (transparency)

An earlier version of this pipeline (v1) reported `h_vulnerable_true = 0 of
200` for the full stratified sample -- see the "Rule-tag breakdown" section
of [`docs/pilot_report_v1.md`](pilot_report_v1.md). That number was itself an
artifact of a sampling bug, not a finding: v1 scanned each era most-recent
first and stopped once its quota was met, so v1's pre-2024 stratum happened
to cluster entirely within 2023-10-06..2023-10-11 -- a period after the
AND-node convention had already fully displaced the old one. Once sampling
was corrected to spread across the full 1999-2023 range (v2 -- see
["Sampling method"](pilot_report_v2.md#sampling-method) in the v2 report),
the true decline pattern became visible. **The defensible, citable number is
43 of 200 overall, not 0 of 200** -- the two are consistent (both show the
convention is gone by 2024+), but only the v2 number is safe to generalize
about pre-2024 CVEs, since v1's pre-2024 sample was not representative of
the stratum's own date range.

## Caveats

- n per year is small (2-3 records), so this is a directional/illustrative
  measurement, not a precise change-point estimate -- the 2002 dip to 0/3 and
  the 2012-2016 transition band should be read as noisy small-sample
  behavior around a real, larger trend, not exact per-year rates.
- The pre-2024 stratum samples one Jan-Apr window per year, not the full
  year (see "Sampling method" in [`docs/pilot_report_v2.md`](pilot_report_v2.md));
  this table reflects that window only.
- Generated by re-classifying the already-collected v2 records
  (`data/pilot_20260905_v2/pre-2024.json`) with `corpus_filter.classify()`
  and grouping by `published` year -- no additional NVD API calls were made
  for this note.
